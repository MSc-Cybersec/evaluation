## Bottom line

No single “unified record” automatically discharges ISO/IEC 27001 or NIST SP 800-53 obligations. Use a linked **Secrets Assurance Record** comprising credential lifecycle evidence, pipeline scanning results, vault/access logs, rotation and revocation events, and exposure-remediation records; together these demonstrate operation of the five secrets-management Mandards.

Approve this evidence model as the system of record, but require auditors to assess control design, operating effectiveness, scope, and ISO Statement of Applicability separately.

## Risk and impact

Four applicable Mandards are **Critical** and one is **High**. Without the records and underlying controls, the organisation cannot reliably demonstrate that exposed credentials were blocked, long-lived credentials were eliminated or rotated, build logs were clean, and detected secrets were revoked and remediated.

The resulting exposure includes unauthorised cloud or production access, persistent credential leakage through repositories and build logs, expanded compromise windows, and audit findings caused by insufficient evidence of control operation.

## Required actions

1. **Block secret exposure in repositories and configuration — Application Security and CI/CD owners.**  
   Per **SECR-M-001**, run secret scanning on every commit or pull request and configure a mandatory failed-build result for high-confidence findings. Remove detected secrets, invalidate them, and replace them with references to an approved secret store.

2. **Prevent persistent exposure in pipelines and images — Platform Engineering.**  
   Per **SECR-M-002**, redact pipeline output, scan completed logs and container images, fail builds on detections, and remove secrets from working directories and command histories before teardown.

3. **Prevent plaintext secrets in build logs — CI/CD owners.**  
   Per **SECR-M-005**, enable masking or redaction, prohibit commands that print sensitive environment variables, and enforce a log-scanning pipeline gate.

4. **Eliminate long-lived production automation credentials — Identity and Cloud Security.**  
   Per **SECR-M-004**, use short-lived OIDC, role-assumption, STS, or equivalent credentials for production automation and run periodic checks for non-compliant long-lived keys.

5. **Enforce CI/CD credential lifetime and rotation — Identity and Platform Engineering.**  
   Per **SECR-M-003**, use temporary credentials with a time-to-live no greater than 15 minutes for interactive credentials and one hour for automated credentials. Rotate remaining stored service-account credentials and API keys at least every 90 days, record every rotation, and automatically revoke overdue credentials.

6. **Adopt a unified evidence key — GRC and Security Architecture.**  
   **Advisory (not knowledge-doc backed):** assign a stable `secret_record_id` to each credential or secret reference and propagate it into vault metadata, pipeline scan results, rotation events, access logs, incidents, exceptions, and remediation tickets. Never place the secret value itself in the assurance record.
