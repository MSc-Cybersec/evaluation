## Bottom line

A new internal REST API should be assessed against all 13 API-domain mandards, but 11 are potentially relevant to REST and two GraphQL-only mandards are not applicable. Internal exposure does not waive authentication, authorization, data-protection, configuration, inventory, or logging controls; approve production release only after the applicable Critical and High controls have evidence-backed verification.

## Risk and impact

The primary exposure is unauthorized access or modification, sensitive-data leakage, privilege escalation, forged identity tokens, denial of service, and insufficient forensic visibility. Applicability depends on API behavior:

## Governing mandards

### Critical

- Per **API-M-001**, *Broken Object Level Authorization Prevention*: verify that the authenticated caller is authorized for each referenced object; unpredictable identifiers are not an authorization control.
- Per **API-M-002**, *Excessive Data Exposure Prevention*: allow-list response fields and exclude credentials, tokens, keys, PII, internal details, and debug information.
- Per **API-M-003**, *Broken Function Level Authorization*: enforce role or permission checks on administrative and privileged operations.
- Per **API-M-004**, *Mass Assignment Protection*: allow-list writable properties through dedicated input DTOs or equivalent mappings.
- Per **API-M-005**, *Auth on Sensitive API*: sensitive endpoints must reject requests without valid authentication with `401` or `403`; the requirement explicitly includes internal APIs.
- Per **API-M-006**, *Rate Limiting Enforced*: public endpoints must produce `429 Too Many Requests` under excessive load. Its mandatory scope is public endpoints, so applicability to this internal API depends on whether it is also publicly reachable.
- Per **API-M-007**, *JWT Signature Validation*: validate every received JWT signature and explicitly reject `alg:none`.
- **API-M-011**, *GraphQL Query Complexity Limits*: applies only if a GraphQL endpoint is introduced, not to REST-only interfaces.

### High

- Per **API-M-008**, *API Security Configuration Baseline*: enforce required security headers, restricted CORS, disabled unnecessary HTTP methods, non-verbose errors, and controlled versioning.
- Per **API-M-009**, *API Inventory & Versioning Management*: maintain an automatically generated OpenAPI inventory, prohibit undocumented production endpoints, and manage deprecation with the prescribed headers and notice period.
- Per **API-M-010**, *API-Specific Audit Logging & Monitoring*: generate structured, sanitized API audit records with identities, outcomes, timings, and correlation IDs, and forward them to the central SIEM.
- **API-M-012**, *Disable Introspection in Production*: applies only to GraphQL production endpoints.
- Per **API-M-013**, *Message-Level Integrity and Confidentiality*: sign sensitive payloads—and encrypt confidential payloads—when TLS terminates at an intermediary or the message crosses an organisational boundary.

## Required actions

1. **API owner and security architect — determine applicability.** Record whether the API handles sensitive data, object IDs, updates, privileged functions, JWTs, TLS-terminating intermediaries, or organisational-boundary crossings. Record **API-M-011** and **API-M-012** as not applicable only if the deployed interface is REST-only.
2. **Development team — implement Critical access controls.** Enforce authentication on sensitive endpoints under **API-M-005**, object-level authorization under **API-M-001**, function-level authorization under **API-M-003**, input allow-listing under **API-M-004**, and response allow-listing under **API-M-002**.
3. **Identity/API platform team — secure tokens.** If JWT is used, validate signatures, trusted issuer and key, and an explicit algorithm allow-list under **API-M-007**.
4. **Platform team — apply the API baseline.** Implement the headers, CORS allow-list, method restrictions, generic errors, and lifecycle controls required by **API-M-008**.
5. **API owner — register the interface.** Generate and maintain the OpenAPI specification, assign ownership, compare deployed routes with documented routes, and control version deprecation under **API-M-009**.
6. **Operations/SOC — enable auditability.** Implement sanitized structured logging, correlation IDs, centralized SIEM forwarding, and monitoring of authentication and authorization failures under **API-M-010**.
7. **Platform team — assess throttling.** Apply **API-M-006** if the API is publicly reachable. **Advisory (not catalogue-backed):** also rate-limit internal endpoints according to caller identity and workload capacity to reduce brute-force and resource-exhaustion risk.
8. **Security architect — assess message protection.** Where a gateway terminates TLS or an organisational boundary is crossed, implement signing and, for confidential payloads, recipient encryption under **API-M-013**.
9. **Governance owner — complete onboarding.** Knowledge document **VeriFy-APP-002**, source: [Application Layer Governance](https://wiki.example-org.internal/wiki/spaces/PMDAAME/pages/659817782), calls for SAF approval and Alfabet onboarding for Azure and on-premises applications, with formal deviations included in the SAF pack. Mandard references: **ASSURE-M-001**, **CLOUD-M-007**, **CRYPT-M-001**, **DATA-M-002**, **GOV-G-006**, **OAUTH-M-001**, **SUPPLY-M-001**.
10. **Identity architect — use the approved internal authentication pattern.** Knowledge document **VeriFy-AUTH-INT-EC-001**, source: [Enterprise Context](https://wiki.example-org.internal/wiki/spaces/PMDAAME/pages/652445334), identifies API Connect for systems integration and lists internal web-service identity options including Entra ID with SAML or OIDC and on-premises LDAPS, Kerberos, or SPNEGO patterns. Mandard references: **AUTH-M-001**, **AUTH-M-002**, **AUTH-M-003**, **CRYPT-M-002**, **GOV-G-006**, **IAM-M-001**, **OAUTH-M-001**, **SAML-M-001**, **SECR-M-001**.
