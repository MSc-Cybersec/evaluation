# G62-K8S

## Question
What Kubernetes controls are required before onboarding a new namespace?

## Sage response

## Bottom line

A new Kubernetes namespace must not be onboarded until access control, secrets protection, network isolation, and pod-security controls satisfy all three Kubernetes Mandards. The principal exposure is credential theft and lateral movement across workloads or namespaces. Platform Engineering should make these controls part of an automated namespace provisioning gate and retain the resulting evidence.

## Risk and impact

| Priority | Exposure if unaddressed |
|---|---|
| Critical | Over-privileged or default service accounts can allow a compromised pod to access the Kubernetes API and move laterally. |
| Critical | Unencrypted or improperly injected secrets can expose credentials through etcd, pod specifications, logs, or process environments. |
| High | Unrestricted pod traffic and privileged workloads can enable cross-workload compromise, host access, and data exfiltration. |

## Governing mandards

- **K8S-M-001 — Kubernetes RBAC & Service Accounts — Critical**  
  Per **K8S-M-001**: each pod or deployment must use a dedicated service account with least-privilege permissions. The default service account must not be used; `ClusterRoleBinding` is prohibited except for monitoring; and RBAC must be audited quarterly.

- **K8S-M-003 — Kubernetes Secrets Management & Encryption — Critical**  
  Per **K8S-M-003**: Kubernetes Secrets must be encrypted at rest using etcd encryption, must not be passed through environment variables, and must use an external secret store. Secret access must be audited and secrets rotated regularly; the catalogue’s actionable guidance specifies 90 days.

- **K8S-M-002 — Kubernetes Network Policies & Pod Security — High**  
  Per **K8S-M-002**: pod-to-pod traffic must be restricted to approved destinations, ingress must authenticate using mTLS or JWT, and pod-security controls must prohibit privileged containers, root execution, writable root filesystems, and host networking.

## Required actions

1. **Establish namespace RBAC — Platform Engineering and application owner**
   - Create a dedicated service account for every workload.
   - Set `automountServiceAccountToken: false` unless Kubernetes API access is explicitly required.
   - Define namespace-scoped `Role` and `RoleBinding` objects with only necessary verbs and resources.
   - Reject wildcard permissions, use of the default service account, and non-monitoring `ClusterRoleBinding` objects.
   - Record the namespace in the quarterly RBAC review process.

2. **Confirm secrets protection — Cluster platform and secrets-management owners**
   - Verify that API-server etcd encryption is enabled through `--encryption-provider-config`.
   - Connect the namespace to an approved external secret store.
   - Prohibit secrets in environment variables and deployment manifests.
   - Establish access auditing and the required rotation schedule.

3. **Apply network isolation — Network or platform security**
   - Install default-deny ingress and egress `NetworkPolicy` objects.
   - Add explicit allow policies only for documented application dependencies, DNS, telemetry, and approved ingress or egress paths.
   - Verify that the cluster’s network plugin enforces Kubernetes NetworkPolicy.
   - Require mTLS or JWT authentication for ingress.

4. **Enforce pod security — Platform Engineering**
   - Configure Pod Security Admission for the namespace at `Restricted`, or at least the catalogue-supported `Baseline` level where formally justified.
   - Enforce non-root execution, no privileged containers, read-only root filesystems, and no host networking.
   - Block admission of workloads that violate these requirements.

5. **Complete the onboarding gate**
   - Run automated policy and security checks before workloads are admitted.
   - Do not approve the namespace while any Critical or High Mandard is unmet.

**Advisory (not catalogue-backed):** add `ResourceQuota`, `LimitRange`, mandatory ownership/data-classification labels, and centralized logging and alerting to the namespace template. No Kubernetes Mandard establishing these as namespace-onboarding requirements was returned.

## Evidence for audit

| Mandard | Minimum evidence |
|---|---|
| **K8S-M-001** | ServiceAccount, Role, and RoleBinding manifests; proof the default account is unused; automount configuration; wildcard and ClusterRoleBinding scan results; latest quarterly RBAC review record |
| **K8S-M-003** | API-server encryption-provider configuration verification; external secret-store configuration; scan proving no secret environment variables or embedded credentials; secret-access audit logs; rotation record |
| **K8S-M-002** | Default-deny and allow-list NetworkPolicy manifests; connectivity test results demonstrating denied unauthorized traffic; Pod Security Admission namespace labels or admission-policy configuration; rejected privileged/root/host-network test deployments; ingress authentication test |
| Onboarding decision | Pipeline or provisioning-job result showing all controls passed, linked to the namespace request and approving owner |
