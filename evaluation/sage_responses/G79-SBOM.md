# G79-SBOM

## Question
What SBOM evidence is required at release and how should it be verified?

## Sage response

## Bottom line

Every release build must produce a **complete, machine-readable SBOM in CycloneDX or SPDX format and publish it as a build artifact**. The release pipeline should block promotion when the SBOM is missing, cannot be parsed, or was not published; production artifacts must also pass signing, signature verification, and producer/consumer binary composition analysis. Release owners should require these records in the release evidence pack or obtain an approved, time-bounded deviation.

## Risk and impact

Failure to produce the SBOM is **Critical** because the organisation cannot reliably identify deployed applications affected by newly disclosed component vulnerabilities. Failure to verify the production artifact is **High** because an altered artifact, unexpected component, embedded secret, or post-scan compromise could reach production.

## Governing mandards

| Mandard | Title | Risk level | Requirement |
|---|---|---:|---|
| **ART-M-002** | Generate SBOM | Critical | Per **ART-M-002**: every build pipeline must generate a complete, machine-readable SBOM, such as CycloneDX or SPDX, and publish it as a build artifact. |
| **ART-M-001** | Artifact Signing & Verification | High | Per **ART-M-001**: production artifacts must be signed and verified before deployment; the final artifact must undergo producer and consumer binary composition analysis for secrets, unexpected components, and integrity violations. |

## Required actions

1. **Generate the SBOM from the final release output — Critical**  
   The DevOps owner must run an SBOM generator such as Trivy, Syft, or CycloneDX tooling during the release build and emit CycloneDX or SPDX.

2. **Publish it as a release artifact — Critical**  
   Store the SBOM in the controlled build or artifact repository alongside the release output. Configure the pipeline to fail if generation or publication fails.

3. **Apply a release gate — Critical**  
   Automatically verify:
   - The SBOM exists.
   - It is non-empty and machine-readable.
   - It parses as the declared CycloneDX or SPDX format.
   - It was generated by the release pipeline and successfully published.

4. **Verify the final artifact — High**  
   Per **ART-M-001**, digitally sign the production artifact, verify the signature before deployment, and block deployment on verification failure. Run binary composition analysis against the final artifact from both producer and consumer perspectives.

5. **Record any exception before release — High**  
   If the release cannot satisfy these controls, it must not proceed through an informal override. A formal deviation must identify the affected control, technical justification, residual-risk owner, compensating controls, independent approval, and expiry.

**Implementation guidance:** The release-management standard specifies build integrity using checksums and signed artifacts, artifact signing, vulnerability scanning, and scanning/signing container images before and after publication. It currently describes CycloneDX SBOM enablement as “Phase 2 in progress.”

**Advisory (not knowledge-doc backed):** Bind the SBOM to the immutable release digest rather than only a mutable version tag, and validate that the SBOM’s component inventory corresponds to the exact artifact being deployed.

## Evidence for audit

The release evidence pack should contain:

- The actual CycloneDX or SPDX SBOM file.
- The successful pipeline record showing SBOM generation.
- The artifact-publication record or repository URI.
- The release identifier, commit, build number, and immutable artifact digest associated with the SBOM.
- The automated gate result proving the SBOM existed, parsed successfully, and was published.
- The production-artifact signature and successful pre-deployment verification result.
- Producer and consumer binary composition-analysis reports.
- Evidence that a negative test blocks release when the SBOM is absent or publication fails.
- Where applicable, an approved and unexpired deviation record.

## Assumptions and limits

The catalogue requires a “complete” SBOM but does not define mandatory component fields, schema versions, completeness thresholds, or SBOM retention periods. The exact artifact-digest binding and schema-validation criteria above are therefore advisory unless established by an additional organisational standard.
